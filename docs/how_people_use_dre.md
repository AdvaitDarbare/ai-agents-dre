# How People Use This DRE Application

This document explains who uses the platform, when they use it in real workflows, and what the day-to-day operating model looks like.

## What This App Is In The Stack

This is a **data reliability control plane** that sits between data production and data consumption.

Typical placement:

1. Data is produced (app DB, events, ETL jobs, vendor feeds).
2. Data lands in files or warehouse tables.
3. DRE validates quality/reliability and enforces policy.
4. Clean data continues to downstream BI/ML; bad data is flagged, quarantined, or remediated.

The app is not a warehouse replacement. It protects trust in data before and during consumption.

## Who Uses It

1. Data Engineers
- Own ingestion pipelines.
- Use DRE to catch schema/quality issues before bad data spreads.

2. Analytics Engineers
- Own models/dashboards.
- Use incidents, lineage, and quality scores to explain broken analytics quickly.

3. Platform/SRE or Data Reliability Owner
- Own alerting, policy gates, and operational posture.
- Use async jobs, incidents, and audit logs for operations.

4. Data Governance/Leads
- Own contract approvals and change history.
- Use HITL approvals, contract versions, and rollback.

## When People Use It In The Process

1. Onboarding new datasets
- Dataset appears with no contract.
- DRE proposes a contract and moves data to pending approval.
- Human approves/rejects, then monitoring becomes automatic.

2. Continuous monitoring
- Event-driven: watcher triggers on new arrivals.
- Orchestrator-driven: Airflow/Dagster triggers DRE checks after pipeline steps.
- Connector-driven: Postgres and optional S3/MinIO datasets are discovered and sampled read-only.

3. Incident response
- A warning/blocked run creates or updates incident context.
- Team uses lineage + diagnostics + anomaly investigation to triage root cause.
- Remediation is proposed and policy/HITL gates control execution.

4. Contract evolution
- Teams update contracts as data evolves.
- Changes are versioned, auditable, and can be rolled back.

## Daily Operating Workflow

1. Check health
- View pulse, incidents, and risk-ranked datasets.

2. Process pending contracts
- Approve/reject proposals for unmanaged datasets.

3. Monitor active datasets
- Trigger evaluate-all job on cadence (for connector-backed datasets).
- Keep watcher running for file-based event-driven checks.
- In production-like mode, keep async worker process running for queued job execution.

4. Investigate issues
- Use anomaly investigation and quality explanation tools.
- Confirm blast radius using lineage.

5. Apply remediation safely
- Proposal generated by engine.
- Execute only when confidence and policy controls are satisfied.

## Recommended Default Mode For This Project

1. Keep deterministic pipeline for core checks.
2. Use one agentic loop for investigation and remediation proposals.
3. Keep policy and HITL strict for mutations/destructive actions.
4. Run event-driven checks for files plus scheduled evaluate-all for connectors.

This gives useful autonomy without introducing non-deterministic pipeline routing.

## Event-Driven vs Orchestrator-Driven

You can use either, or both:

1. Event-driven
- Best for file drops and near-real-time reliability checks.
- Watcher reacts when data lands.

2. Orchestrator-driven
- Best for warehouse/model jobs in Airflow/Dagster.
- DRE is called as a step/sensor in existing DAGs/jobs.

Most teams run both:
- Event-driven for ingestion edges.
- Orchestrator-driven for warehouse/model checkpoints.

## What “Good” Adoption Looks Like

1. New datasets are always onboarded via contract proposal/approval.
2. Critical datasets have incidents triaged within a defined SLA.
3. Fewer downstream dashboard/model failures from upstream drift.
4. Contract and remediation changes are fully auditable.
